## № 1 Эксперименты с параллелизмом в Python: сравнение однопоточного, многопоточного и многопроцессорного подходов.

В данном эксперименте сравниваются три подхода к выполнению задач:
- **Однопоточность** - последовательное выполнение
- **Многопоточность** - использование нескольких потоков в одном процессе
- **Многопроцессорность** - использование нескольких процессов

### CPU-bound задания
|       Подход        |  Время  |
|---------------------|---------|
| Однопоточность      |  2.22 с |
| Многопоточность     |  2.18 с |
| Многопроцессорность |  1.13 c |

**Вывод:** По результатам было получено, при CPU-bound задачах многопроцессорность выполняет вычислительные задания быстрее, чем однопоточность примерно в 2 раза, многопроцессорность быстрее для CPU-bound задач, потому что каждый процесс имеет свой собственный GIL, и процессы выполняются параллельно на разных ядрах процессора. В многопоточности GIL не позволяет потокам выполняться одновременно на CPU, поэтому время почти не отличается от однопоточного подхода.

### CPU-bound задания на большом количестве ядер
|       Подход        |  Время  |
|---------------------|---------|
|        5            |  1.11 с |
|        10           |  1.21 с |
|        40           |  1.26 c |
|        80           |  Ошибка |

**Вывод:** Увеличение количества процессов с 5 до 80 не ускоряет время выполнения кода это связано с тем что:
- Создания процессов занимает временя поэтому при увелечение ядер время будет только увеличиваться.
- При превышении числа физических ядер процессора начинаются накладные расходы на переключение.
- Количество процессов имеет ограниченное количество физических ядер увеличивая количесво ядер, можно поймать ошибку `ValueError: max_workers must be <= 61`, обосновано тем, что `max_workers` не может превышать 61 на Windows. Это связано с ограничениями операционной системы на количество процессов.
**Рекомендация:** Для CPU-bound задач оптимально использовать количество процессов, равное числу ядер процессора.

### Вопрос: Сколько процессов создавать под 10 000 задач?

**Вывод:** Для 10 000 задач, необходимо создать столько процессов, сколько ядер у процессора.

|---------------------|---------|
| Однопоточность      |  9.59 с |
| Многопоточность     |  2.84 с |
| Многопроцессорность |  3.12 с |

**Вывод:**  Для I/O-операций многопоточность и многопроцессорность дают схожий результат, но потоки потребляют меньше памяти

## Общие выводы по эксперименту №1

- **CPU-bound**:  Эксперимент показал, что однопоточность и многопоточность схожи во времени выполнения разница в 0.02 секунды, а многопроцессорность показала себя идеально и быстрее **в 2 раза**.
- **I/O-bound**:  Многопоточность и многопроцессорность выдали близкие значения, но в I/O-bound заданиях проще будет использовать потоки, так как они потребляют меньше памяти, чем многопроцессорность.
- В многопоточности GIL не проблема для I/O (блокировка освобождается при ожидании), но тормозит CPU-вычисления. В многопроцессорности GIL не проблема для CPU-вычислений, у каждого процесса свой GIL и каждый работает не мешая другому.

## № 4 Эксперимент использование декораторов:

В данном эксперименте рассматриваются три типа декораторов:
- **timer** - измерение времени выполнения функции
- **retry** - автоматическое повторение при ошибках
- **cache_result** - кеширование результатов

### Что такое декоратор?

- **Декоратор** - это функция, которая принимает функцию и возвращает новую функцию с расширенной функциональностью. Декоратор представляет собой обертку, в которую мы оборачиваем исходную функцию, добавляя новую логику.
```
def deco(func):
    def wrapper(*args, **kwargs):
        ...
    return wrapper

@deco
def func():
    return
```
- **functools.wraps** - метод, который сохраняет метаданные функции (докстринг, имя функции).

### Кастомный cache_result vs встроенный lru_cache

|        Параметр        |   Кастомный  |  Встроенный |
|------------------------|--------------|-------------|
| Работа со списками     |      Да      |     Нет     |
| Работа со словарями    |      Да      |     Нет     |
| Контроль размера кеша  |      Нет     |     Да      |
|      Скорость, с       |    0.00014   |    0.00017  |

### Вопрос: `{(1, 2): 'x'}` работает, `{(1, [2]): 'x'}` — нет.
- `{(1, 2): 'x'}` - работает по той причине, потому что  ключи списка могут быть только неизменяемые типы данных, в данном случае ключом является кортеж, кортеж это неизменяем тип данных он хешируемый и имеет внутри числа 1 и 2, которые тоже являются не изменяемыми типами данных.
- `{(1, [2]): 'x'}` — не работает из-за того что в кортеже в неизменяемом типе данных содержится изменяемый тип данных список. Кортеж в целом становится **нехешируемым**, так как его содержимое может измениться. Python не может гарантировать неизменность ключа, поэтому выбрасывает ошибку `TypeError: unhashable type: 'list'`.

## Выводы по эксперименту №4
- **cache_result** — это универсальный инструмент, который может работать с любыми типами данных.
- **lru_cache** — это стандарт, который работает только с хешируемыми типами.
- Эксперимент показал, что **cache_result** и **lru_cache** скорости выполнения равны.

## № 5 Эксперимент использование генераторы, итераторы, контекстные менеджеры:

В данном эксперименте рассматриваются:
- **Генератор** - функция, которая генерирует значения по одному (yield)
- **Итератор** - объект с методами __iter__ и __next__
- **Контекстный менеджер** - управление ресурсами через with

### Что такое генераторы, итераторы, контекстные менеджеры?
- Итератором называется объект, по которому можно проитерироваться. Он имеет два метода: `iter` - итерируемый объект и `next` - это следующий элемент, а когда элементы заканчиваются — выбрасывает `StopIteration`. 
- Генератор — это подвид итератора: функция, которая генерирует значения. Генератор не хранит элементы в оперативной памяти, а вычисляет их по заданному правилу, поэтому занимает очень мало места. Генератор объявляется как обычная функция, но вместо инструкции return в нём используется yield.
- Контекстный менеджер  - это объект, который позволяет встроить функционал на входе и выходе на блока with. Есть два способа создать свой контекстный менеджер: 1) это создать класс, в котором реализовать дандер-методы __enter__ и __exit__, 2) метод импортировать contextmanager из модуля contextlib и использовать декоратор @contextmanager, который применяется к функции-генератору и использовать всё, что до yield — это вход, а после — выход.

### Генератор читает файл кусками vs наивный `f.read()`

|        Параметр        |   Генератор  |   f.read()  |
|------------------------|--------------|-------------|
|     Чтение файла       |   По частям  |  Полностью  |
|        Память          |    0.02 МБ   |   50.01 МБ  |

### Класс vs contextmanager

|        Параметр        |     Класс    |   contextmanager  |
|------------------------|--------------|-------------------|
|         Код            |  Пишем класс |     Декоратор     |
|        Гибкость        |    Высокая   |       Низкая      |
|       Читаемость       |    Хорошая   |      Хорошая      |

### Замыкания и `nonlocal`: пример с `make_counter()`
- В первом случае у нас выходит исключение UnboundLocalError, по той причине потому что вложенная фунцкия не видит `count` в своей области видимости и при указании `nonlocal`, мы указываем, чтобы `count` берется из внешней функции. 

## Выводы по эксперименту №5 
- **Генератор vs f.read():** Генератор читает файл в **3.3 раза быстрее** и использует **в 2500 раз меньше памяти**!

## № 6 Эксперимент использование идемпотентность, REST:

### Что такое идемпотентность, идемпотентный ключ и REST?
- Идемпотентность - это свойство HTTP-метода, при котором повторный запрос с теми же данными не меняет состояние сервера.
- Идемпотентный ключ - это ключ который мы применяем, чтобы идентифицировать уникальный запрос, чтобы гарантировать, что повторный запрос не создаст новый, а вернет сохранненый результат. 
- Rest - это набор принципов по которому мы стоим API: 
1. Разделение ответственности между клиентом и сервером. Ответственность клиента — пользовательский интерфейс, ответственность сервера — данные. 
2. Отсутствие состояния. Каждый запрос должен быть независимым, как будто он сделан в первый раз. Сервер не должен хранить какую-либо информацию о клиенте. Каждый запрос клиента к серверу должен содержать всю информацию, необходимую для обработки этого запроса. 
3. Единый интерфейс. Интерфейс обращения к серверу одинаков для всех и не зависит от клиента. 
4. Многоуровневость. Самое важное чтобы не было нарушение правило клиент-сервер, многоуровневость строится на том что сервер будет клиентом для другого сервера. 
5. Кешируемость. Данные ответа могут быть закешированы. Это значит, что полученные данные можно сохранить на клиенте, а при идентичном запросе взять их из памяти клиента — кеша, а не ждать их с сервера.
6. Код по запросу. Этот принцип необязательный. Он гласит, что функциональность клиента может быть расширена кодом, приходящим с сервера.

### Голые сокеты

### Ожидания `requests.get` vs  `requests.Session()`
- У `requests.get` при каждом запросе будет создаваться новое TCP соединение приблизительное время одного соединение равно 0.000934 секунды, при 20 запросов время выполнения будет равно 0.018 секунд.

**Вывод:**
- Session показал что о быстрее на 0.023 c get это примерно на 36% Session быстрее, чем get. 
- HTTP — это текст поверх TCP. Библиотеки скрывают эту рутину, но под капотом происходит то же самое — открытие сокета, отправка запроса, чтение ответа.

## № 8 Эксперимент JWT-аутентификация и WebSocket

### Технологии
- **JWT** — для аутентификации
- **bcrypt** — для хеширования паролей
- **WebSocket** — для двусторонней связи в реальном времени
- **AuthX** — библиотека для JWT в FastAPI

### Эндпоинты

|   Метод   |     Эндпоинт   |               Описание                 |
|-----------|----------------|----------------------------------------|
|    POST   | `/registerate` |     Регистрация нового пользователя    |
|    POST   |    `/login`    |   Вход в систему (выдача JWT-токена)   |
|    GET    |  `/get_login`  | Проверка авторизации (требуется токен) |
|   POST    |    `/logout`   |    Выход из системы (удаление cookie)  |
| WebSocket |      `/ws/`    |       WebSocket-соединение для чата    |

**Примечание** В папке `test` написаны pytest тесты на проверку эндпоинтов.

**Вывод:**
- 1. **JWT-аутентификация** - ключ аутентификации пользователя. Используется для запросов к защищенным методам API.
- 2. **Cookies** — это фрагмент данных, в которых сервер передаёт важную информацию о клиенте.Браузер получает этот фрагмент, сохраняет его и с каждым последующим запросом отсылает обратно на сервер.
- 3. **CORS** - это механизм безопасности браузера, ограничивает запросы с одного сайта к API на другом домене. Обозначают в http заголовках кто и как может обращаться к нашему серверу.
 1. Браузер отправляет **preflight-запрос OPTIONS**
 2. Сервер отвечает заголовками:
 - `Access-Control-Allow-Origin` — кто может обращаться
 - `Access-Control-Allow-Methods` — какие методы разрешены
 - `Access-Control-Allow-Headers` — какие заголовки разрешены
 - `Access-Control-Allow-Credentials` - можно ли передавать куки
- 4. **WebSocket** - протокол прикладного уровня, который работает поверх ТСР-соединения, стартует также как и HTTP-запрос с заголовками 'Upgrate': websoket, 'Connection': Upgrate. Если сервер поддерживает, он переключает на проткол WebSocket. В отличие от HTTP он содержит постоянное TCP-соединение, причем дуплексное, то есть клиент и сервер может олтправлять запросы в любой момент времени.
