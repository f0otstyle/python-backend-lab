## LLM: токены, контекст, вызов API

- **LLM**, большая языковая модель: нейросеть, которая генерирует и анализирует текст и код. Упрощённо, ответ строится последовательным предсказанием следующих токенов.
- **Токен**: фрагмент текста — например, часть слова или знак; не обязательно целое слово.
- **Промпт**: твой запрос или инструкция модели.


### Контекстное окно: что входит и кто отвечает

**Контекстное окно** — максимум токенов, которые модель видит за один вызов. В него складывается всё:

```
system-промпт + история диалога + описания инструментов
  + retrieved-документы + вопрос пользователя + место под ответ
```

Переполнение = ошибка запроса (400) или молчаливая обрезка. Отсюда техники:

- ограничивать историю (последние N сообщений);
- суммаризировать старый диалог вместо пересылки целиком;
- RAG вместо «запихнуть всю базу знаний».

###  Генерация и параметры: temperature и недетерминизм

Генерация идёт по одному токену; на каждом шаге модель даёт **распределение вероятностей** по всем токенам, а параметры решают, как из него выбирать:

| Параметр | Что делает | Когда какой |
|---|---|---|
| `temperature` | Масштабирует распределение: 0 — всегда самый вероятный токен; выше — больше хаоса и разнообразия | 0–0.3 — классификация, извлечение, код; 0.7+ — креативный текст |
| `top_p` | Отсекает хвост маловероятных токенов | Обычно не трогают вместе с temperature |
| `max_tokens` | Жёсткий потолок длины ответа | **Всегда ставить** |
| `stop` | Стоп-последовательности | Для парсимых форматов |

Ключевой нюанс: **temperature=0 не гарантирует байт-в-байт одинаковые ответы.**

## Промптинг и структурированный вывод

## Системный промпт = спецификация поведения

Системный промпт —  должен состоять из спецификация сервиса: что делает, что запрещено, в каком формате отвечает, что делать при неуверенности. Хороший системный промпт для бэкенд-задачи содержит:

1. **Роль и задачу** — одна задача;
2. **Ограничения** — что запрещено, на каких данных работать;
3. **Формат ответа** — точная структура;
4. **Поведение при неуверенности** — «если данных не хватает — верни поле unknown, не выдумывай». Без этого пункта модель **уверенно галлюцинирует**, потому что пустой ответ противоречит её обучению;

## Few-shot: примеры сильнее инструкций

**Few-shot** — пара примеров «вход → выход» прямо в промпте. Модель ловит формат и граничные случаи из примеров часто лучше, чем из абзаца инструкций.

Правила:

- 2–5 примеров обычно достаточно;
- примеры должны покрывать **граничные случаи**: пустой отзыв, смешанный тон, нерелевантный текст;
- примеры показывают и **отказы**: «нерелевантный текст → category=other» — так модель учится не пытаться классифицировать что угодно;
- keep consistency: формат примеров = формат, который требует схема, один в один.

## Структурированный вывод: три механизма

Заставить модель вернуть парсимые данные можно тремя способами, по возрастанию надёжности:

| Механизм | Гарантия | Нюанс |
|---|---|---|
| «Верни JSON» в промпте | Никакой: markdown-блоки, запятые, комментарии | Не использовать для контракта |
| **JSON mode** | Валидный JSON | Не гарантия, что поля — **твои** |
| **Structured outputs / JSON Schema** | JSON по твоей схеме — у части провайдеров это constrained decoding: грамматикой запрещены токены, ломающие схему | Лучшая опция; но пустые/бессмысленные значения схема не отсечёт |

## Конвейер невалидного ответа

Даже со structured output модель может отказать, вернуть бессмыслицу в полях, обрезать ответ на max_tokens. Конвейер:

```
вызов → парсинг+валидация (pydantic)
          ├─ ok → дальше по бизнес-логике
          └─ fail → retry с обратной связью (до 2–3 попыток):
               «Ты вернул: {raw}. Ошибка: {validation_error}.
                Верни JSON ровно по схеме: {schema}»
                    ├─ ok → дальше
                    └─ fail → fallback:
                         лог (промпт, сырой ответ, ошибка) + бизнес-действие
                         (дефолтная категория / тикет человеку / 503 клиенту)
```

Ключевая деталь, которую часто опускают: **retry с обратной связью** работает в разы лучше слепого повтора — модель видит свою ошибку и валидационное сообщение. А лимит попыток обязателен: у модели нет совести, есть распределение.

Это ровно тот же паттерн, что весь модуль очередей: ненадёжный шаг → ретраи → лимит → DLQ/fallback → метрики (сколько невалидных, сколько fallback'ов).
