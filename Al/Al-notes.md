## LLM: токены, контекст, вызов API

- **LLM**, большая языковая модель: нейросеть, которая генерирует и анализирует текст и код. Упрощённо, ответ строится последовательным предсказанием следующих токенов.
- **Токен**: фрагмент текста — например, часть слова или знак; не обязательно целое слово.
- **Промпт**: твой запрос или инструкция модели.


### Контекстное окно: что входит и кто отвечает

**Контекстное окно** — максимум токенов, которые модель видит за один вызов. В него складывается всё:

```
system-промпт + история диалога + описания инструментов
  + retrieved-документы + вопрос пользователя + место под ответ
```

Переполнение = ошибка запроса (400) или молчаливая обрезка. Отсюда техники:

- ограничивать историю (последние N сообщений);
- суммаризировать старый диалог вместо пересылки целиком;
- RAG вместо «запихнуть всю базу знаний».

###  Генерация и параметры: temperature и недетерминизм

Генерация идёт по одному токену; на каждом шаге модель даёт **распределение вероятностей** по всем токенам, а параметры решают, как из него выбирать:

| Параметр | Что делает | Когда какой |
|---|---|---|
| `temperature` | Масштабирует распределение: 0 — всегда самый вероятный токен; выше — больше хаоса и разнообразия | 0–0.3 — классификация, извлечение, код; 0.7+ — креативный текст |
| `top_p` | Отсекает хвост маловероятных токенов | Обычно не трогают вместе с temperature |
| `max_tokens` | Жёсткий потолок длины ответа | **Всегда ставить** |
| `stop` | Стоп-последовательности | Для парсимых форматов |

Ключевой нюанс: **temperature=0 не гарантирует байт-в-байт одинаковые ответы.**

## Промптинг и структурированный вывод

## Системный промпт = спецификация поведения

Системный промпт —  должен состоять из спецификация сервиса: что делает, что запрещено, в каком формате отвечает, что делать при неуверенности. Хороший системный промпт для бэкенд-задачи содержит:

1. **Роль и задачу** — одна задача;
2. **Ограничения** — что запрещено, на каких данных работать;
3. **Формат ответа** — точная структура;
4. **Поведение при неуверенности** — «если данных не хватает — верни поле unknown, не выдумывай». Без этого пункта модель **уверенно галлюцинирует**, потому что пустой ответ противоречит её обучению;

## Few-shot: примеры сильнее инструкций

**Few-shot** — пара примеров «вход → выход» прямо в промпте. Модель ловит формат и граничные случаи из примеров часто лучше, чем из абзаца инструкций.

Правила:

- 2–5 примеров обычно достаточно;
- примеры должны покрывать **граничные случаи**: пустой отзыв, смешанный тон, нерелевантный текст;
- примеры показывают и **отказы**: «нерелевантный текст → category=other» — так модель учится не пытаться классифицировать что угодно;
- keep consistency: формат примеров = формат, который требует схема, один в один.

## Структурированный вывод: три механизма

Заставить модель вернуть парсимые данные можно тремя способами, по возрастанию надёжности:

| Механизм | Гарантия | Нюанс |
|---|---|---|
| «Верни JSON» в промпте | Никакой: markdown-блоки, запятые, комментарии | Не использовать для контракта |
| **JSON mode** | Валидный JSON | Не гарантия, что поля — **твои** |
| **Structured outputs / JSON Schema** | JSON по твоей схеме — у части провайдеров это constrained decoding: грамматикой запрещены токены, ломающие схему | Лучшая опция; но пустые/бессмысленные значения схема не отсечёт |

## Конвейер невалидного ответа

Даже со structured output модель может отказать, вернуть бессмыслицу в полях, обрезать ответ на max_tokens. Конвейер:

```
вызов → парсинг+валидация (pydantic)
          ├─ ok → дальше по бизнес-логике
          └─ fail → retry с обратной связью (до 2–3 попыток):
               «Ты вернул: {raw}. Ошибка: {validation_error}.
                Верни JSON ровно по схеме: {schema}»
                    ├─ ok → дальше
                    └─ fail → fallback:
                         лог (промпт, сырой ответ, ошибка) + бизнес-действие
                         (дефолтная категория / тикет человеку / 503 клиенту)
```

Ключевая деталь, которую часто опускают: **retry с обратной связью** работает в разы лучше слепого повтора — модель видит свою ошибку и валидационное сообщение. А лимит попыток обязателен: у модели нет совести, есть распределение.

Это ровно тот же паттерн, что весь модуль очередей: ненадёжный шаг → ретраи → лимит → DLQ/fallback → метрики (сколько невалидных, сколько fallback'ов).

## Декомпозиция

### Теория

Мега-промпт «сделай X целиком» даёт средний результат по всем осям сразу. Декомпозиция = шаги, где каждый шаг: (а) проверяется отдельно, (б) имеет свой контекст, (в) даёт точку отката.

Три способа резать:

| Способ | Правило | Пример |
|---|---|---|
| По потоку данных | следующий шаг ест результат предыдущего | схема → хендлер → тест |
| По риску | самое рискованное — первым; узнал рано — перепланировал дёшево | сначала гонка, потом стиль |
| По тестируемости | шаг готов, только когда его можно запустить | эндпоинт без запуска — не шаг |

Паттерн **«план до кода»**: первый промпт любой задачи — «покажи план, код не пиши». План дёшево критиковать, код дорого переписывать.

## Роли: линза, а не биография

- Роль — **фильтр внимания**: что модель считает важным, каким языком отвечает, какие стандарты применяет. Роль НЕ добавляет знаний — модель та же, «20 лет в бигтехе» не грузит в неё новый опыт. Иногда биография даже вредит: уверенный тон растёт, честное «не знаю» — падает.

| Роль помогает | Роль — шум |
|---|---|
| узкий фокус ревью (как проверяющие в workflow) | фейковые заслуги («лучший в мире») |
| формат объяснения («как джуну-коллеге, без аналогий») | роль-заменитель контекста (роль ≠ код/файлы) |
| системные промпты суб-агентов: у каждого своя линза | инсценировки ради «фактов» |


# Что такое субагенты в программировании

Субагент — это специализированный ИИ‑агент, которому оркестратор (главный агент) делегирует отдельную подзадачу.

## Как устроена типичная мультиагентная схема
- Оркестратор принимает запрос пользователя, декомпозирует его на подзадачи, решает, кого вызвать и в каком порядке, затем собирает итоговый результат. Сам он не делает «грязную» работу — только управляет.
- Субагенты получают узкую задачу, свой набор инструментов и ограниченный контекст. Например: code_writer пишет код, security_checker ищет уязвимости, explainer объясняет простым языком.
- Передача данных между агентами обычно идёт через JSON‑сообщения: task_id, описание задачи, входные данные, ожидаемый формат результата.

## Практические примеры субагентов для типичных задач

|Субагент|Задача|
|---|---|
|code_reviewer|Проверка кода на соответствие стандартам, поиск уязвимостей|
|test_generator|Генерация unit/integration‑тестов|
|refactor_assistant|Рефакторинг без изменения поведения|
|doc_generator|Создание README, комментариев, Swagger/OpenAPI|

**Почему субагент не общается с пользователем** — если сабагенту нужно что‑то спросить, он либо отвечает на основе контекста, либо завершает работу с пометкой «не хватает данных». Спрашивать пользователя — задача оркестратора. Иначе у пользователя одновременно живут пять чатов от пяти сабагентов, и никто, включая сам оркестратор, не понимает, кто что делает.

**Параллельность** — оркестратор может запустить несколько субагентов одним шагом и блокируется до завершения всех. Это упрощает синхронизацию (никаких очередей и колбэков на стороне оркестратора), но накладывает естественное ограничение: задача делится на параллельные ветви, у которых нет кросс‑зависимостей. Если зависимости есть, лучше последовательный вызов.

**Что мы у себя гоняем через субагентов:**

- Прогон ревью‑чеклистов по всему PR / по всему модулю (пакет → сабагент).
- Триажинг issue из трекера (GitHub / GitLab / YouTrack): воспроизводится / не воспроизводится, severity, дубли (один сабагент на батч issue).
- Инвентаризация фич продукта (один сабагент на функциональную область).
- Сборка полной документации проекта (по модулям).
-Поиск code smells по списку правил (батч связанных правил → один сабагент).

- **Ошибка при декомпазиции:** при работе с оркестратором и субагентами: «давайте у нас будет субагент‑планировщик, субагент‑кодер, субагент‑тестировщик и субагент‑ревьюер на каждой задаче». Звучит логично но, мы потратим много токенов на пересказ друг другу того, что предыдущий уже сделал.

**Хорошие границы для разделения:**
- Независимые исследовательские области (исследование разных модулей, разных issue, разных правил ревью).
- Слабо связанные модули с чистым интерфейсом (фронт и бэк по контракту).
- Чёрный ящик‑проверка: тесты, прогон линтера, прогон бенчмарка, не нужен контекст реализации.

**Плохие границы:**
- Последовательные фазы одной фичи (план → код → тест), слишком много общего контекста.
- Сильно связанные компоненты, которым нужно много синхронизироваться.
- Задачи, требующие общего разделяемого состояния.

- При использование субагентов, типичный пользователь напишет "Запусти проверку RP через субагентов" и каждый раз оркестратор будет по разному разбивать задачи, так как обладает свойством динамического планирования, решение данной проблемы это использование скиллов создая файл SKILL.md.

**Скилл** — упакованная инструкция: папка с файлом SKILL.md, которую модель загружает по триггеру, а не держит в контексте постоянно. Триггер — совпадение задачи с description из frontmatter либо явный вызов /имя-скилла. До триггера тело скилла не занимает в контексте ни строчки.

**Зачем:** при чисто динамическом планировании оркестратор каждый раз разбивает одну и ту же задачу по-разному — порядок шагов, команды и проверки зависят от конкретного прохода. Скилл фиксирует пайплайн один раз текстом: «выпуск релиза» всегда проходит через одни и те же шаги → выполнение воспроизводимо, модель импровизирует только внутри шага, но не в его последовательности.

**Признаки хорошего SKILL.md:**

- Жёсткие нумерованные шаги и явное «выполняй ровно по порядку, не пропускай».
- Команды проекта зафиксированы в тексте.
- Границы: что не трогать, когда остановиться и спросить.
- Точка подтверждения пользователя перед необратимым шагом: merge, push, публикация пакета.


# Харнес

- Это обвязка во круг модели, которая несет свои правила, лимиты, ограничения и тд.

**Три уровня инжиниринга:**

- Prompt engineering — формирует инструкции, которые модель получает.
- Context engineering — управляет тем, что модель видит и когда.
- Harness engineering — включает оба предыдущих плюс всю прикладную инфраструктуру: оркестрацию инструментов, персистентность состояния, восстановление после ошибок, циклы верификации, обеспечение безопасности и управление жизненным циклом.

**Хук (hook)** — скрипт, который harness запускает принудительно на определённом событии жизненного цикла сессии. Модель не может «передумать» его выполнять — исполнение не зависит от её воли.

**Семь событий** (других нет): SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Stop. Самые полезные: PreToolUse (фильтр перед инструментом), PostToolUse (автопроверка после правки).

**Конфиг**: `<repo>/.zcode/config.json`.  Хуки выключены по умолчанию — без `"enabled": true` молча не работают.

**Как идёт вызов**: модель хочет Bash → клиент ловит PreToolUse → запускает скрипт → на stdin кладёт JSON {"tool_name": ..., "tool_input": {command}} → exit 0 = пропустить, exit 2 = заблокировать (агент видит stderr-причину).

- При открытие чужого проект → первый взгляд: есть ли .zcode/config.json с секцией hooks. Чужие хуки в незнакомом репозитории = чужой код исполняется на твоей машине при первом же вызове тула, без твоего ведома. Уровень доверия к хукам = уровень доверия к автору репозитория. Это тот же принцип, что и с MCP-серверами: workspace-конфиг применяется автоматически, «открывай только воркспейсы, которым доверяешь».

## Скилл против хука: кто что исполняет

| | Скилл | Хук |
|---|---|---|
| Знает | КАК работать: шаги, порядок, зачем | ЧТО НИКОГДА: инварианты |
| Исполняет | модель (может адаптировать и **пропустить шаг**) | клиент (пропустить невозможно) |
| Природа | текст в контексте, ленивая загрузка | код, исполняется принудительно |
| Сила | гибкость, рассуждение | детерминированность |
| Пример | «сначала план, потом код, потом ревью» | «SPEC всегда полный, .py всегда компилируется» |

**Хук не может заменить скилл.** Событие хука — фиксированная точка жизненного цикла клиента (тул-вызов, промпт, старт/стоп), а не «этап работы». Клиент не знает, что наступил «этап ревью» — этапы существуют только в плане скилла, который исполняет модель. Хук не умеет рассуждать (ревью делать не может) — он умеет три вещи: механическая проверка, подсунуть контекст, пас/стоп.

**Что хук может вместо понимания этапа — enforcing артефакта.** «Коммит только после ревью» делается PreToolUse/Bash с matcher `git commit` → проверить, что файл отчёта ревью существует → нет отчёта → exit 2. Этап выражен не пониманием, а следом на диске.

**Живая пара из моей лабы:** скилл spec-tdd-pipeline задаёт этапы (спека → TDD → merge), хук spec_check принуждает инвариант (SPEC.md без Цель/Шаги/DoD/Границы отклоняется). И главный эмпирический факт из прогонов: **проверка после действия — совет** (агент может проигнорировать пометку об ошибке — проверено живьём), **проверка до действия — запрет** (deny не даёт плохой версии попасть на диск). Инвариант ставят до действия.
