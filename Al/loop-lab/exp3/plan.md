# exp3 — план: простая система заказов такси на FastAPI

> План до кода: кода нет, сначала согласование. После «делай» — реализация по шагам из раздела 4.

## 1. Сущности (таблицы БД)

| Имя | Поля | Связи |
|---|---|---|
| passengers | id (PK), name, phone | 1 → N rides |
| drivers | id (PK), name, phone, car, status (`available` / `busy` / `offline`) | 1 → N rides |
| rides | id (PK), passenger_id (FK), driver_id (FK, NULL до назначения), pickup, dropoff, status (`created` → `assigned` → `in_progress` → `completed` / `cancelled`), price (int, копейки), created_at, updated_at | N → 1 passengers, N → 1 drivers, 1 → 1 payments |
| payments | id (PK), ride_id (FK, уникальный — один платёж на поездку), amount (int, копейки), status (`pending` / `paid` / `failed`), idempotency_key (уникальный), created_at | 1 → 1 rides |

## 2. Эндпоинты

| Метод | Путь | Назначение | Коды |
|---|---|---|---|
| GET | /health | живость сервера (политика лабы) | 200 |
| POST | /passengers | создать пассажира | 201, 422 |
| GET | /passengers/{id} | посмотреть пассажира | 200, 404 |
| POST | /drivers | создать водителя | 201, 422 |
| GET | /drivers | список водителей, фильтр `?status=available` | 200 |
| PATCH | /drivers/{id} | сменить статус водителя (например, offline) | 200, 404, 422 |
| POST | /rides | создать заказ; с `Idempotency-Key` повтор не плодит дубликат, а возвращает первый ответ | 201, 404 (пассажир не найден), 422 |
| GET | /rides | список заказов, фильтры `?passenger_id=`, `?status=` | 200 |
| GET | /rides/{id} | посмотреть заказ | 200, 404 |
| POST | /rides/{id}/assign | назначить свободного водителя | 200, 404, 409 (нет свободных / заказ не в `created`) |
| POST | /rides/{id}/start | начать поездку | 200, 404, 409 (заказ не в `assigned`) |
| POST | /rides/{id}/complete | завершить поездку, освободить водителя | 200, 404, 409 (заказ не в `in_progress`) |
| POST | /rides/{id}/cancel | отменить заказ, освободить водителя | 200, 404, 409 (заказ уже `completed` / `cancelled`) |
| POST | /payments | оплатить завершённую поездку; `Idempotency-Key` обязателен: повтор возвращает первый ответ, второй платёж по той же поездке — 409 | 201, 404, 409 (уже оплачена / не `completed` / другой ключ на оплаченную поездку), 422 |

## 3. Компоненты

| Компонент | Библиотека | Зачем |
|---|---|---|
| HTTP-фреймворк | fastapi (уже в requirements лабы) | роутинг, валидация, автодоки /docs |
| ORM | sqlalchemy — ⚠ нужна твоя явная «да», AGENTS.md запрещает добавлять зависимости без спроса | связи FK, транзакции; схему создаёт `create_all`, без миграций |
| БД | sqlite (stdlib, файл exp3.db) | без отдельного сервера, для лабы достаточно |
| ASGI-сервер | uvicorn (уже в requirements) | запуск стенда |
| Схемы тел запросов | pydantic (идёт с fastapi) | валидация входа, типы полей |
| Клиент сценариев | aiohttp (уже используется в exp1/exp2) | параллельные запросы, ретраи, «Итог: N/M» |

## 4. Порядок реализации

1. **Каркас.** `server.py` c `/health`, модели SQLAlchemy, подключение к SQLite, `create_all`. Проверка: `python -m py_compile *.py`; сервер поднят, `GET /health` → `{"status": "ok"}`; файл exp3.db создан.
2. **Пассажиры и водители.** POST/GET/PATCH из раздела 2. Проверка: POST → 201, GET → 200/404, запись видна в списке; PATCH меняет статус водителя.
3. **Заказы.** `POST /rides` + `GET /rides[/{id}]` с идемпотентностью по `Idempotency-Key` (хранение первого ответа — опыт exp2). Проверка: два одинаковых POST с одним ключом → один заказ в БД и одинаковый `id` в ответах; без ключа → два заказа.
4. **Жизненный цикл.** assign/start/complete/cancel с проверкой допустимых переходов статуса; статус водителя меняется в той же транзакции, что и заказ. Проверка: happy path до `completed`; неверный переход → 409; после assign `driver.status = busy`, после complete/cancel — снова `available`.
5. **Оплата.** `POST /payments` только для `completed`, уникальный `ride_id`, идемпотентность по ключу. Проверка: первый POST → 201; повтор с тем же ключом → тот же ответ и одна запись в БД; POST по неоплаченной, но не завершённой поездке → 409.
6. **Конкурентность.** Два параллельных assign на один заказ и два параллельных платежа с разными ключами (назначение и оплата — в транзакции с условным `UPDATE ... WHERE status=...`). Проверка: сценарием в клиенте — ровно один 200/201, второй 409; в БД один водитель и один платёж.
7. **Клиент client_1.py.** Полный сценарий: пассажир → водитель → заказ (с повтором и без) → assign → start → complete → pay → повтор pay → ретраи. Проверка: клиент печатает «Итог: N/M ...» — политика лабы, автотестов нет.
8. **notes.md в exp3.** Прогноз → Факт → Почему разошлись по каждому сценарию. Проверка: заметки заполнены после прогонов, прогнозы были записаны до запуска.

## 5. Риски и узкие места

- **Конкурентность назначения (гонка read-check-write).** Два параллельных assign успевают оба прочитать `status=created` и назначить двух водителей. Лечение: транзакция + условный `UPDATE rides SET driver_id=... WHERE id=? AND status='created'` и проверка числа затронутых строк, а не «прочитал-проверил-записал».
- **Дубли заказов при ретраях.** Клиент ретраит POST после таймаута — плодятся одинаковые заказы. Лечение: `Idempotency-Key` + уникальный индекс по ключу, повтор возвращает первый ответ (схема exp2).
- **Двойное списание при оплате.** Ретрай платежа = две записи в payments. Лечение: уникальный `ride_id` в payments + идемпотентный ключ; без ключа платёж отклоняется.
- **Идемпотентные ответы в памяти.** Хранилище ключей в памяти умирает при рестарте сервера — после рестарта ретрай создаст дубликат. Для лабы допустимо, но честнее хранить ключи в БД рядом с заказом.
- **SQLite блокировки записи.** Одна пишущая транзакция за раз; конкурентные записи дают `database is locked` без `busy_timeout`. Для лабы хватает; для продакшена это PostgreSQL.
- **Невалидные переходы статусов.** start без assign, cancel после complete — каждый мутирующий хендлер обязан проверять текущий статус, иначе 409; иначе рассинхронизация со статусом водителя.
- **Деньги.** Не хранить цену float'ом (округления) — только int в копейках; расчёт цены фиксированный на этапе заказа, не в платеже.
- **Рассинхронизация статуса водителя.** PATCH /drivers/{id} мимо жизненного цикла заказа может сделать «занятого» водителя свободным с активным заказом. Лечение: busy/available менять только внутри транзакций assign/complete/cancel.
