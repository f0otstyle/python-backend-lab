# Ревью фичи (фиксированный пайплайн)
> Зачем: фича готова только после независимого ревью свежими глазами —
> автор своё не видит (заполняет пробелы головой).

1. **Скоуп.** Файлы фичи называет пользователь; не назвал — git status/diff
   по папке фичи, список на подтверждение.
   Зачем: ревью без скоупа расползается по всему репо.
2. **Ревьюер.** Спавн py-reviewer; передать пути файлов (не содержимое!) и
   задачу фичи одной строкой. Свои объяснения кода НЕ передавать.
   Зачем: fresh eyes — ревьюер должен увидеть код впервые.
3. **Находки.** Принять отчёт в формате P0–P3.
4. **Триаж.** P0/P1 — обязательный фикс до коммита; P2/P3 — списком юзеру,
   решает он. Зачем: не каждая находка стоит токенов и риска.
5. **Фикс-цикл.** Чинит агент (не ревьюер!) → повторный шаг 2–3 на
   изменённых файлах. Максимум 3 итерации.
   Зачем: стоп-условие — иначе цикл «чинил-находил» бесконечен.
6. **Верификация.** Прогон тестов/скрипта фичи запуском, не «на глаз».
7. **Отчёт В ЧАТ:** находки с судьбой (исправлено/отклонено юзером/осталось),
   вердикт «готова к коммиту: да/нет».

## Границы
- Ревьюер только читает (tools=[Read, Grep, Glob]).
- Агент не коммитит — коммит за пользователем.
- Спорная находка → решает юзер, решение фиксируется в отчёте.
- Ревьюер недоступен → честный отчёт и стоп. Не имитировать ревью собой.
- Готово = P0/P1 закрыты или отклонены юзером + верификация зелёная.
